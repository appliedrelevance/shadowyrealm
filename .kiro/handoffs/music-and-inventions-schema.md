# Handoff: a schema for Music, head-counts for Inventions, sign-in for both

Three changes to the shared Supabase project, for one session in the monorepo. All three belong to the
monorepo, which owns the shared database's migrations and its Auth configuration.

1. **Music gets its own schema**, `music`: the third site on the ShadowyRealm platform, with the same
   tables as `shadowyrealm` and `inventions`. It weighs only benefit; its harm columns exist and stay
   at zero, so every site has the same tables.
2. **Inventions counts people**: the head-count and evidence columns and four-place link strengths that
   `shadowyrealm` got in `20261115071456_shadowyrealm_system_one_scoring`.
3. **Google sign-in** returns to `inventions.shadowyrealm.com` and `music.shadowyrealm.com`. This takes
   in `.kiro/handoffs/inventions-redirect-url.md`; if that one has been done, only Music's entry is new.

Nothing here changes a row that exists, and the deployed Workers keep working throughout: they select
named columns, and no deployed site reads the `music` schema.

## Steps

1. **Record Inventions before**, on the cloud:
   ```sql
   select count(*), sum(strength) from inventions.relationships;   -- 558, 90.39 on 2026-11-23
   select count(*) from inventions.assessment_periods;              -- 945
   ```
2. **Apply `inventions-people-counts.sql` to the cloud** as migration `inventions_people_counts`, in one
   transaction.
3. **Apply `music-site.sql` to the cloud** as migration `music_site`, in one transaction.
4. **Expose `music` through the Data API on the cloud**, only after step 3 has committed. Read the current
   list first and append to it:
   ```sql
   select rolconfig from pg_roles where rolname = 'authenticator';
   -- then, with the list exactly as read plus music:
   alter role authenticator set pgrst.db_schemas = '<the list as read>, music';
   notify pgrst, 'reload config';
   notify pgrst, 'reload schema';
   ```
5. **Apply both files to gideon** in the same order, each in one transaction, with a row in
   `supabase_migrations.schema_migrations` for each carrying the cloud's version and name. Add `"music"`
   to `[api] schemas` in `supabase/config.toml`, with a comment line like the one for `inventions`.
6. **Copy both files** into `supabase/migrations/<cloud version>_<name>.sql` and commit them, with the
   `config.toml` change, on `main`.
7. **Auth redirect URLs**, cloud only (Authentication → URL Configuration → Redirect URLs; Management API
   `uri_allow_list` in `/v1/projects/qgfmwstgkwyqqwyqroav/config/auth`). Read the list, then add whichever
   of these is missing: `https://inventions.shadowyrealm.com/**`, `https://music.shadowyrealm.com/**`.
   Leave `https://priorart.shadowyrealm.com/**` where it is.

## What must not be done

- **Never `db reset`** either database. Both hold every property's production data.
- **Never expose `music` before its schema exists.** A name in `pgrst.db_schemas` with no schema behind it
  makes the schema cache unloadable and 503s every REST request for every property (PGRST002, the outage
  of 2026-08-09).
- **Never replace a list.** `pgrst.db_schemas` and `uri_allow_list` are each one comma-separated string;
  setting either to only the new entry removes every other property's. Append to the value as read.
- **Never change the Auth Site URL.** Every property falls back to it.
- **Never fill the new Inventions columns by hand.** The Worker fills them when it re-scores each period.
- **Never edit the SQL.** If it is wrong, say so; it is fixed in `tools/site-schema.ts` in the shadowyrealm
  repo and generated again.

## How to check it

- Inventions, on the cloud and on gideon:
  ```sql
  select column_name from information_schema.columns
  where table_schema = 'inventions' and table_name = 'assessments' order by ordinal_position;
  select numeric_precision, numeric_scale from information_schema.columns
  where table_schema = 'inventions' and table_name = 'relationships' and column_name = 'strength';
  select count(*), sum(strength) from inventions.relationships;
  ```
  The last eleven columns are `prosperity_benefit_people` … `environment_harm_people`, then `evidence`.
  The strength is 5 and 4. The counts and sum match step 1.
- Music, on the cloud and on gideon:
  ```sql
  select enum_range(null::music.entity_type), enum_range(null::music.relationship_type);
  select table_name from information_schema.tables where table_schema = 'music' order by 1;
  ```
  `{person,group,style,work,instrument}`, `{genre,gave_rise,member,made,influence}`, and the five tables
  `assessment_periods`, `assessments`, `entities`, `entity_audit_log`, `relationships`.
- The Data API serves it: `curl -s "https://qgfmwstgkwyqqwyqroav.supabase.co/rest/v1/entities?select=id&limit=1"
  -H "apikey: <anon key>" -H "Accept-Profile: music"` answers `[]`, and the same request with
  `Accept-Profile: blog` and `/rest/v1/published_posts` still answers rows.
- Sign-in: on `https://inventions.shadowyrealm.com/login`, Google sign-in returns to
  `https://inventions.shadowyrealm.com/`, signed in.
